---
name: atlas-review
description: Use a ScreenAtlas project to inspect screen contracts, iterate on visual references, respond to pinned feedback, and import application screenshots with exact evidence identities.
---

ScreenAtlas is a local workbench alongside the application repository. Find the
user-selected folder containing `atlas.json`. Run `atlas --project <folder>`
commands there; `python -m atlas` is equivalent from the source checkout.
Use `--help`, `templates`, `inspect`, and `context SCREEN` to obtain the current
schema, project digest, contracts, connections, prompts, and review revisions.

Read the relevant product behavior and visual direction before changing a
screen. Contracts own behavior; image references do not establish behavior,
native operation, accessibility, or release readiness. ScreenAtlas edges describe
intended routes rather than verified application routing.

When setting up a new app, begin the guided conversation after installation;
browser buttons are optional. The project handoff names the staged workflow.
Ask a few brief app questions, then request two or three user-supplied inspiration
images and wait for them. Generate two or three separate mood images from those
inputs before designing screens. Default to atmosphere, palette, lighting,
materials, and texture without UI components or typography; include either only
when explicitly requested. Store supplied references as kind=anchor nodes and
generated moods as kind=sheet nodes in a dedicated Inspiration group, with no
navigation actions. Keep original inputs and actual provenance. Stop for the user's
direction review before app screen generation. Record the chosen direction and
exact approved reference identities in a supporting document. Use those mood
images as visual inputs for subsequent screens and revisions, link contracts to
the direction document, and preserve actual input digests in provenance. Continue
an existing approved direction without repeating the interview unnecessarily.

For pinned feedback, read the complete thread and its exact image identity.
Use `status ID in_progress --revision N --operation UUID`, then implement the
requested work. Replies support `--body-file`, `--preview PNG`, and `--status
ready`. A reply preview is only an attachment. Resolve feedback only when the
reviewer has authorized that disposition.

Every review mutation needs a stable operation UUID (`atlas new-id`). Keep it
and the complete command payload for uncertain-response retries. Reusing that
UUID with changed content fails. A stale revision requires reading concurrent
changes and deliberately reconciling them, not blindly increasing the number.

For image generation, use the tool actually available in this agent session.
ScreenAtlas cannot invoke Codex's built-in Image Gen, and this skill does not grant
access to one. If no suitable tool is available, explain the limitation and
accept a user-provided output. Do not substitute a paid API without direction.
Retain generated bytes and the exact submitted prompt. Record input image
digests, output identity, known tool details, protected layout/colors, and
limitations without inventing missing provenance.

Import a registered candidate with `import-proposals MANIFEST --operation UUID`.
Entries target an existing stable node ID and require `baselineSha256` (the
current curated digest, or null for a new screen), `candidate`, and `prompt`.
Optional `original`, `versionId`, `source`, `reviewNote`, and `provenance` retain
context. File paths are relative to the manifest. Create topology first for a
new screen; importing an unknown ID never creates a node or approval.

Acceptance is an explicit reviewer decision about an exact candidate. Never
infer it from a positive reply, a resolved thread, generation completion, or
an implementation request. The browser supports acceptance while the image is
loaded. The CLI also supports explicit reviewed decisions for an authorized
reviewer. Promoting the currently accepted version is separate and requires
its identity and expected project digest. It changes curated files, never Git
commits, pushes, publishing, or application code by itself.

After implementing the application, obtain an actual screenshot through tools
available for that platform. Do not label a reference render as a real capture.
Import with `import-captures MANIFEST --operation UUID`; preserve capture UUID,
screen ID, state, source (device/simulator/archive), device/OS, and known build
details. Unknown build identity remains unknown. Scenario entry and screenshot
automation belong to the user's application, not to ScreenAtlas. Stable ScreenAtlas IDs
can label those application-owned scenarios and evidence.

Capture-specific feedback and appearance approval remain attached to that
capture. A new capture starts pending; old comments and approval do not move.
Appearance approval requires the matching current curated reference and does
not establish behavior or release readiness.

`check` reports inventory errors and authoring warnings. `doctor` verifies the
review schema and recorded images. `backup` retains private history and images;
`restore` verifies a backup into a new folder. `export` creates a read-only HTML
file and excludes local review content unless `--include-review` is explicit.
Do not publish or share project content without the user's authorization.
